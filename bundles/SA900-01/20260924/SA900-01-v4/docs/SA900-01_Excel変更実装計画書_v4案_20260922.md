## 3. 現状の出力②の計算を整理する

以下の記号は説明用であり、Excelの新しい名前定義や新関数を必須にするものではない。単位はmm。

| 記号 | 意味 | 現在の参照元 |
|---|---|---|
| TH | 全高 | `塔内機器_入力①!B20` |
| T | 行程 | `塔内機器_入力①!P20` |
| Pit | ピット深さ | `塔内機器_入力①!B26` |
| S | 最初の取付位置。最下階FLを0とした高さ | `T/2 + 計算用シート!Y34`。現値は加算500 |
| E | 最後の取付位置。同じFL基準 | `計算用シート!Y26`。後落ち・横落ちで算出式が異なる |
| N | 合計取付箇所数 | `計算用シート!Y37`。ケーブル用とテール用の合計 |
| P | 中間を配置する切上げ間隔 | `ROUNDUP((E-S)/(N-1),0)` |

後落ちは行程に機種区分の補正を加える。横落ちは行程から制御盤下端の寸法と補正295を引く。全高は必要個数の選定などに、行程は始点・終点やテール用個数の条件に使う。FL基準の出力②では、上端の幾何学的な上限を`TH−Pit`としている。

各位置は、最初をS、途中をSにPを順次加えた値、最後をEに固定している。したがって、**平均間隔を切り上げると、最後の1区間は他より短くなる**。この最後の区間まで正であるかを確認する必要がある。

現在は丸める前の`E>=S`と個数などを確認しているが、丸めた後の最終区間を確認していない。R1では既存の設計定数や丸め方を変えず、この不足を補う。

## 4. R1 — 出力②の配置成立判定

### 再現した問題

基準入力は、全高24,470、行程20,145、ピット1,300、合計取付3箇所。`帳票基本入力!C8`を「横落ち」、`C9`を9,277にすると、次の結果になる。

```text
S = 20,145 / 2 + 500 = 10,572.5
E = 20,145 - 9,277 - 295 = 10,573
P = ROUNDUP((10,573 - 10,572.5) / 2, 0) = 1

1箇所目: 10,572.5
2箇所目: 10,573.5
3箇所目: 10,573
最後の間隔: -0.5
```

`塔内機器_出力②!M38`が−0.5になり、`計算用シート!Y39`は1のまま、ステータスは「参照範囲内（設計妥当性は要照合）」のままだった。Excelの数式エラーではないため、エラーセルを数えるだけでも発見できない。

同じ横落ち・制御盤寸法で行程を20,144、最初の階高を3,744として階高合計を合わせると、S=E=10,572となり、3箇所が同位置になる。これも正常表示された。

### 採用する仕様

1. 入力・個数が成立する場合だけ、表示用セルとは独立した補助セルでS、P、最終間隔を計算する。
2. 2≦N≦9の整数、P>0、最終間隔>0を必要条件とする。既存の上端制約`E<=TH−Pit`も維持する。
3. 不成立時は取付位置、FLからの寸法、間隔、個数・タイプなど出力②の計算結果を空欄にし、出力②のステータスに理由を表示する。入力の再掲欄と帳票の枠は残す。
4. 係数500・295、後落ち補正、個数表、40,000・80,000の閾値、ROUNDUPと終点固定の規則は変更しない。
5. 最後の位置を勝手に延長したり、ROUNDUPをROUNDDOWNに置き換えたりして、見かけ上成立させない。

全ての途中の間隔がPであるため、最終区間は次の式で判定できる。

```text
last_gap = E - (S + (N - 2) × P)
valid = 入力成立 AND 個数成立 AND P > 0 AND last_gap > 0
```

N=2でも同じ式を使え、`last_gap=E−S`になる。Nが未入力、1以下、不正値の場合は、除算前に終了する。最小施工間隔が別に規定されている可能性はあるが、根拠のない数値を追加しない。「正の間隔」は数学的な必要条件であり、施工可能性の保証ではない。

この判定と全位置の厳密昇順が一致することを、N=2〜9、整数・0.5を含む開始位置、正・零・負の範囲幅の計1,424組で別計算して確認した。これは提案する数学条件の確認であり、下記Excel数式の実装済み検証やi-Reporter実機検証ではない。

## 5. R2 — 出力①の不要時と検索範囲外

### 再現した問題

**不要時:** 基準入力から`帳票基本入力!C7`だけを「Cwtｾﾌﾃｨなし」に変更すると、出力①の個数欄M19は空文字になる。計算シートのD4:D9はこの表示用空文字に1を加えて除算するため、6セルが数式エラーになる。COMのエラー値は−2146826273（#VALUE!相当）。帳票の明細が空欄でも、内部計算は正常ではない。

3. 必要個数がある場合は、検索前に位置が床面表の表現範囲に入ることを確認する。
4. 最初の位置が最下階FLより下になる場合、今回の修正版では出力①の位置・手配計算結果を止め、「出力①：最下階FL未満の位置を表現できません。設計条件を確認」と表示する。

| 両出力が不成立 | 出力①の理由 | 出力②の理由 | 入力→出力①→出力②の優先順。個別欄に両方を保持 |

計算!Y23は、Y15が不成立ならY16、それ以外ではAH41、AH36、既存Y18の順に最初の該当メッセージを返す。出力①のB89ではAH41、出力②のB75ではAH36を優先し、個別警告がない場合はY23を表示する。出力③のB75はY23を表示する。これにより、他出力の警告だけが表示されて、自分の空欄理由が分からなくなることを防ぐ。

計算!AH42に候補の版識別を1か所で保持し、3枚の既存版表示欄から参照する。これは保守時に検証済みのファイルを識別するための変更であり、帳票の配置変更は伴わない。メッセージの折返し・縮小表示は、既存欄の範囲内で読めることをExcelとiPhoneで確認する。本文が収まらない場合は意味を保って短文化し、黙って切り捨てない。

## 7. R3 — 検証を修正の一部として整える

### 現状と必要な範囲

現行の`verify_output2_v3.ps1`は静的検証とExcel試験を実行するが、最終サマリーを作成する`summarize_output2_v3.py`は呼び出さない。サマリー生成側も100件固定で判定し、通常保存・再オープン結果には同じ候補SHAとの結び付けがない。

今回のv3について、既存サマリーと現在のSHAの一致は確認できている。「現在の検証記録が虚偽」という指摘ではない。今後の失敗・中断時に、以前の成功サマリーを最新結果として使わないための変更である。

### 実装方法

既存の検証資産を再利用し、v4用の入口を1つ作る。言語の統一や全面的なビルド基盤の作り直しは行わない。

```text
verify_sa900_v4.ps1
  1. 対象パス・元v3のSHA・候補SHA・試験計画SHA・run_idを記録
  2. 今回の状態をrunningとして新しい実行ディレクトリに記録
  3. 数式・依存関係・DB・レイアウト・保護の静的検証
  4. 同じ候補のExcel再計算・比較・不変条件検証
  5. 候補と同一バイトの一時コピーで通常保存・再オープン試験
  6. 全結果のrun_idと検査対象SHAを照合
  7. passedまたはfailedの最終サマリーを一時ファイルから置換
```

試験中に候補が変わった場合は失敗扱いとする。強制終了でrunningが残った場合も合格扱いにしない。過去の合格履歴は保存するが、latestの状態がrunning/failedなら配布不可とする。

保存試験で一時コピーのバイト列がExcelによって変化すること自体は許容する。コピー作成時の入力SHA、保存後SHA、再オープン結果を記録する。実際に配布する候補は試験中に上書きしない。候補自身を保存し直す工程がある場合は、その工程を先に完了し、最終SHAに対して検証を開始する。

件数は試験計画から求める。期待する全ケースIDが1回ずつ完了し、skipがないことを確認する。`len(cases)==100`という固定値を将来も合否判定の根拠にしない。

### テストの考え方

- 従来100ケースは可能な限りそのまま再利用する。v3の表示結果との一致を維持しつつ、不要な内部計算セルの空欄化など意図した差分はセル・条件・理由を指定して許可する。
- 「旧版と同じ」と「数学的条件を満たす」は別の検査にする。正しくない旧版結果に合わせる試験を書かない。
- 既存の独立計算例に加え、位置の厳密昇順、最終位置一致、FLと寸法の再構成、上限内、未使用行空欄を独立に確認する。
- 数値0、空文字、真の空セル、数値に見える文字列を区別する。画面の見た目だけで判定しない。

### 最低限必要な試験表

| 試験群 | 入力・操作 | 期待結果 |
|---|---|---|
| 基準 | 現在の保存入力 | 通常の出力①②③の結果を維持。変更対象の版・警告・不要な内部セルだけ許容 |
| 既存回帰 | 既存100ケース | 期待結果と一致。変更理由のない差分0 |
| R1負間隔 | 横落ちC9=9,277、T=20,145 | 出力②停止、配置警告。数式エラー0 |
| R1零間隔 | 上記にT=20,144、最初の階高3,744 | 出力②停止、配置警告 |
| R1隣接正値 | 横落ちC9=9,276、T=20,145 | 最終間隔+0.5。数学判定は成立。施工適合を断定しない |
| 既存の不成立 | 横落ちC9=9,278 | 元の幾何条件で停止。新しい循環やエラーなし |

| 行程閾値 | 40,000・80,000の直前・一致・直後 | テール用個数とタイプが現行規則どおり。幾何条件を満たす入力セットを作る |

| R2検索下限外 | 1-2、TH=11,000、T=3,745、Pit=6,000 | 出力①のみ停止・警告。出力②の成立する位置は維持 |
| R2検索境界 | 同条件でPit=5,499／5,500／5,501 | 位置5,500がFLより上／一致は成立、下は停止 |
| R2不要＋深ピット | 深ピット条件でCwtなし | 不要として正常終了。検索しない |

| 連続変更 | 正常→不成立→不要→正常 | 全て再計算され、古い位置・個数・警告が残らない |
| 検証の失敗 | 意図的に1ケース失敗／途中中断 | 最新状態が合格にならない。以前の成功記録で代用しない |
| 候補違い | 検証途中に候補コピーを差替え | SHA不一致で失敗。別候補の記録を混ぜない |

全高、行程、ピット、階高合計が矛盾したまま閾値だけ変えたテストを「正常例」にしない。期待値は具体的な入力セットとともに試験計画へ保存する。

静的検証では、変更予定セルと実際の差分の一致、循環参照なし、外部ブック参照の新規追加なし、禁止関数なし、既存DB値・印刷設定・保護方針の維持を確認する。追加した補助セルは編集保護の対象に含める。

### i-Reporterでの確認

Excel上での合格後、利用可能な帳票定義に候補を反映する。実機反映は実装段階で明示された検証環境で行い、本番配布と混同しない。

最低限、基準・負間隔・零間隔・正の隣接値・Cwtなし・深ピット・FL境界一致・正常から不成立への連続変更を確認する。各ケースで、計算結果、空欄化、警告、保存後の再オープンをExcelの期待値と照合する。iPhone機種、iOS、i-Reporter・帳票定義の版を記録する。

公式の対応関数一覧に基づき、既存で使うIF・ROUNDUP・VLOOKUP等の範囲で構成する。AND/ORはIF条件内で使用する。新たにLET・XLOOKUP・動的配列・VBAへ依存する設計にはしない。[i-Reporter公式・Excel関数の利用](https://manuals.i-reporter.jp/create-a-form/prepare-the-formexcelfile/excelfunctions)

今回の主目的は正しさである。小さな補助計算追加による影響は実機で観察するが、測定していない高速化率や時間短縮は成果に含めない。公式情報でも、数式やIF・VLOOKUPの量は読込み時間の一因であり、関数の数だけで所要時間を断定できるものではない。[i-Reporter公式・入力帳票を開くのに時間がかかります](https://help.i-reporter.jp/knowledge/入力帳票を開くのに時間がかかります)

## 8. DBについて今行うこと・更新前に必要なこと

### 今回の修正版

既存DB値を変更しない。推定データを自動的に確認済へ昇格させない。数式修正を理由に、補完済みのDBまで設計確認済と扱わない。既存のDB差分検査を維持する。

### 確認記録の弱点と、対応が必要になる時点

試験内で`塔内機器_出力②_DB!V23:Z23`へ確認情報を入れるとAA23=1になる。その後、確認対象の部品組合せI1080を別文字列へ変えてもAA23=1のままで、出力③J14に変更後の値が表示された。現在の確認式は必要項目が埋まっているかを確認しており、確認したデータと今のデータが同一かは確認していない。

これは保護を解除した保守操作の試験である。現在のDB不変を要求する静的検証は、この変更を検出できる。したがって、「現行の全検証をすり抜けた」とは評価しない。

**DBの変更を正式に許す運用へ移る前、または推定グループを初めて確認済へ移す前**に、次の最小運用を導入する。

1. 対象グループのID、適用条件、上下限、部品組合せ、関係するルールの版から、確認対象を固定する記録を作る。
2. 管理スクリプトでそのデータのSHAを算出し、根拠資料・資料版・確認者・確認日とともに保存する。
3. DB変更時は対象グループの旧確認を失効させる。変更前の確認を引き継いだまま配布しない。
4. 配布時の検証で、確認対象SHAと現在のデータを照合する。不一致は配布失敗とする。

この処理をiPhoneのセル関数に追加する必要はない。まず既存の作成・検証スクリプトに小さく追加する。対象データをそのまま並べる形式と数値型を固定し、書式・作成日時だけの変更で失効しないようにする。外部DBサーバーや認証基盤は今回の要件からは不要。

本項の追加実装が実際に必要になった場合は、別途約1〜2時間を見込む。今回の約10時間には含めない。現在のDBをそのまま使う修正版では、DB不変の検証を必須条件とすることで範囲を限定する。

## 9. 今回採用しない改善案

| 案 | 今回見送る理由 | 再検討する条件 |
|---|---|---|
| 数式数・MAX・VLOOKUPをさらに一括削減 | v3で出力②の式文字数は9,039→4,331、IF記述251→118まで削減済み。残りの数自体から実害は確定できない | 実機測定で特定計算が遅さの原因と分かった場合 |
| 1,120行の部品DBを同じ値ごとに全面統合 | 現在同じ組合せでも、適用機種や将来の改訂条件が同じとは限らない。推定コピーの一致を設計上の同一性と扱えない | メーカー資料で共通性・適用条件が確認され、保守負担の実績がある場合 |

## 11. 配布可能とする条件・残る判断

次の全てを満たすことを、今回の変更に対する完了条件とする。

- R1・R2の再現問題が解消し、正常条件での意図しない計算差分がない。
- 全試験で内部を含め数式エラー0、循環参照0。必要ケースが未実施・途中中断でない。
- 出力中の取付位置が厳密昇順、最終位置一致、FL変換整合を満たす。
- 原本・v2・v3のSHAが変わらず、既存DB値も変わっていない。
- 元の帳票印刷設定、1ページの出力②、既存入力規則・編集保護を維持する。管理用補助セルも保護する。
- 通常保存・再オープンで修復要求がなく、同じ候補の記録である。
- iPhone側で代表ケースが一致し、必要な警告が読める。未実施なら「PC検証済・実機未検証」と明記し、i-Reporterでの完了扱いにしない。
- 今回変更していない設計定数や推定DBについて、検証範囲以上の「施工適合」「メーカー承認済」を表示しない。

未確定の設計情報があっても、R1の数学的な不成立の拒否、R2のエラー防止と表現不能時の停止、R3の検証改善は実装できる。最小施工間隔を新設することや、最下階FL未満の取付を新たに表示することは、その情報が確認できるまで実装しない。

候補に回帰が見つかった場合は配布を止め、v4を修正する。v3へ戻すだけで今回の問題が解消したとは扱わない。元版の保存は再現・比較・復旧のためであり、既知の問題を含む版を無条件で本番推奨するものではない。

本計画の受入れは、今回提案した変更が意図どおりに動くことの確認である。元設計全体の認証や、未照合の補完DBの適合証明を代替しない。
